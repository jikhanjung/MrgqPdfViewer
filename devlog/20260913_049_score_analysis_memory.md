# 049 — 악보 분석 메모리: PdfBox 엔진 대신 경량 콘텐츠 해석기 (할당 905MB → 19MB) + 실기기 측정

작성일: 2026-09-13
선행: [`046`](20260913_046_score_layout_in_app.md)(악보 분석 도입), [`048`](20260913_048_min_sdk_30.md)(API 21 OOM 계기)

---

## 0. 요약

악보 분석이 API 21 에뮬레이터에서 OOM 으로 죽었다(#048). 재 보니 최대 힙은 30MB 대였지만 **13쪽 분석에 905MB 를
할당**하고 GC 가 60번 돌았다. 원인은 PdfBox-Android 의 콘텐츠 스트림 처리(토큰화 + 연산자). 분석 경로에서 PdfBox
엔진을 빼고 필요한 연산자만 읽는 **경량 해석기**(`PathContentInterpreter`)로 바꿨다.

| Moldau0607.pdf 13쪽 (에뮬레이터 API 30) | PdfBox 엔진 | 경량 해석기 |
|---|---|---|
| 시간 | 7.4초 | **0.19초** (약 39배) |
| 할당 | 905MB | **19MB** (약 47배) |
| 최대 힙 증가 | 37MB | **8MB** |
| GC 횟수 | 50~65 | **3~4** |

**Z18TV Pro 실기기**(32bit ARM, RAM 2GB)에서 `몰다우.pdf` 8쪽 첫 분석 **556ms**. 실기기 확인 중 버그 2개를 찾아 고쳤다(§6).

## 1. 측정 방법

추측으로 고치지 않았다. 임시 계측 테스트(커밋 안 함)로 단계마다 잰다:

- 시간: `System.nanoTime`
- 할당: `Debug.getRuntimeStat("art.gc.bytes-allocated")` 차이
- 최대 힙: 2ms 간격 샘플러 스레드로 `totalMemory - freeMemory` 최대값
- GC: `art.gc.gc-count` 차이

## 2. 가설 1 — 글꼴 파싱 (기각)

분석은 경로만 보는데 PdfBox 엔진은 `Tf`/`Tj`/`TJ` 마다 내장 글꼴을 읽는다. 텍스트 연산자를 건너뛰게 해 봤지만
**할당 904MB 로 그대로**였다. 텍스트 연산자는 59개뿐이었다. 되돌렸다.

## 3. 단계별로 쪼개기

| 단계 | 시간 | 할당 |
|---|---|---|
| `PDDocument.load` | 47ms | 2MB |
| **13쪽 `processPage`** | **7.1초** | **901MB** |
| `StaffSystemDetector.detect` | 20ms | 0.8MB |

압축 해제한 콘텐츠는 **3.1MB**, 경로 박스는 8,642개. 입력의 약 290배를 할당한다. 판정 코드는 무시할 수준이고,
박스를 미리 걸러도(59% 만 남음) 이득이 없었다.

연산자 이름별로 나누고, 토큰 파싱만 따로 쟀다:

| 구간 | 할당 |
|---|---|
| **토큰 파싱만** (`PDFStreamParser.parseNextToken`, 토큰 43만 개) | **633MB** (토큰당 약 1.5KB) |
| `c` 곡선 (29,159회) | 174MB (6.2KB/회) |
| `l` 직선 (31,377회) | 59MB |
| `cm` (4,299회) | 15MB |
| `m`, `q`, `rg`, `Tf` … | 각 1~12MB |

2/3 가 토큰화, 1/3 이 곡선·직선 처리. 라이브러리 안쪽이라 설정(`MemoryUsageSetting` 등)으로는 줄지 않는다.

## 4. 설계 — `PathContentInterpreter`

콘텐츠 스트림 바이트를 직접 읽는다. 파이썬 `segment_score.py` 도 PdfBox 없이 직접 파싱했다.

- **필요한 연산자만**: `q Q cm m l c v y re h f F f* B B* b b* S s n W W* Do`. 나머지(텍스트·색·선 속성)는 피연산자만 비운다
- **숫자는 `FloatArray` 스택**에 바로 누적 파싱 — 토큰 객체를 만들지 않는다
- **그래픽 상태 스택은 배열을 재사용** (`q` 8,700회에도 할당 없음)
- 문자열 `( )`(중첩·이스케이프), `< >`, 배열·딕셔너리 안의 값, 주석, **인라인 이미지 바이너리**(`BI … ID … EI`)를 건너뛴다
- `Do`: Form XObject 면 행렬을 곱해 실행(깊이 8 제한). 폼 안의 `Q` 가 바깥 상태를 꺼내지 못하게 바닥을 둔다
- 순수 Kotlin — JVM 단위 테스트 21개로 문법 경계 사례를 고정

PdfBox 는 `PdfBoxContent`(스트림 압축 해제·Form XObject 조회)에만 남았다.

### 같은 박스를 내는가

기존 PdfBox 수집기를 androidTest 의 **기준 구현**(`PdfBoxPathCollector`)으로 옮기고,
`PathInterpreterEquivalenceTest` 가 Moldau 13쪽 **모든 박스를 하나하나**(개수·곡선 여부·좌표 0.01pt) 대조한다.
골든 테스트는 판정 결과만 보므로, 그 앞 단계인 입력이 같다는 것을 따로 보인다.

변이 검사 — `c` 에서 제어점 하나를 박스에 넣게 바꾸면:

| | 단위 | 대조 | 골든 |
|---|---|---|---|
| 곡선 제어점 포함 | ❌ 실패 | ❌ 실패 (`p1 박스 88 y0: PdfBox 620.04 vs 해석기 611.52`) | ✅ 통과 — 못 잡음 |

곡선 박스는 음표 머리 판정에만 쓰여 마디 결과가 안 바뀐다. **대조 테스트를 따로 둔 이유가 확인됐다.**

### APK 크기

release APK 가 4.78MB → 5.75MB. 해석기 때문이 아니라 **minSdk 30**(#048) 때문이다: minSdk 28 이상이면
`classes.dex`(2.49MB)·`resources.arsc` 를 **압축하지 않고** 담는다(설치 후에는 압축 해제본을 따로 두지 않아 오히려 작다).

## 5. 실기기 측정 — Z18TV Pro

`adb connect 192.168.55.75` 로 연결해 직접 확인한 기기 정보:

| 항목 | 값 |
|---|---|
| OS | **Android 14 (API 34)**, 보안 패치 2025-10-05 — #048 의 "Android 11" 은 출고 사양이었다 |
| CPU | armeabi-v7a (32bit ARM), 보드 HP4610-Mecool 계열 |
| 메모리 | 1.9GB, 앱 힙 한계 256MB |
| 설치돼 있던 앱 | v0.1.12 (release 서명) |

### 설치

- 설치된 v0.1.12 와 로컬 release 빌드의 **서명 인증서가 같은지 먼저 확인**(SHA-256 `dece2981…9c65734`) — 달랐다면 데이터를 지워야 했다
- `adb install -r` 업데이트 설치. TV 에 "이전 버전의 Android 용" 경고(targetSdk 30)가 떠 사용자가 허용했다
- 기존 PDF 6개와 설정 유지, **DB v4 → v7 마이그레이션 실데이터 통과**, release 빌드의 PdfBox 문서 정보 읽기 동작 확인 (CI 에서는 확인된 적 없던 경로)

### 측정

release 서명 계측 테스트로 재려 했지만 러너가 `NoClassDefFoundError: androidx/tracing/Trace` 로 죽었다 — R8 이 앱에서
`androidx.tracing` 을 걷어냈다(러너는 앱 쪽에서 찾는다). 재설치(경고 재허용)를 피해 **실사용 경로로** 쟀다:
사용자가 리모컨으로 `몰다우.pdf` 를 열고 마디 박스를 켰다.

| 항목 | 결과 |
|---|---|
| `몰다우.pdf` 첫 분석 (8쪽, 시스템 16) | **556ms** |
| 분석 후 앱 Java 힙 | 9.4MB |
| 분석 시각 긴 GC 로그 | 없음 |
| 화면 | 두 페이지 모드에서 박스 정합, 번호 = 인쇄 번호 |

PdfBox 엔진은 실기기에서 재지 못했다(에뮬레이터에서만 7.4초/13쪽).

## 6. 실기기에서 발견해 고친 것

### ① 끝세로줄에 가짜 마디

8쪽 마지막 시스템 끝의 **끝세로줄(가는 선 + 굵은 선)** 자리에 폭 5pt 짜리 마디 "64" 가 생겼다(인쇄상 마지막은 63).

- 굵은 선은 폭이 2pt 를 넘어 마디선 후보가 아니다 → 마지막 마디선은 가는 선(548.3), 오선 끝은 553.0
- 파이썬에서 옮긴 규칙은 "마지막 마디선이 오선 끝과 **4pt** 넘게 떨어지면 오선 끝을 경계로 추가" → 4.7pt 라 추가됐다
- 수정: 남은 폭이 **최소 마디 폭(15pt) 이상**일 때만 추가. 골든(Moldau0607: 552.7 vs 553.0)은 그대로
- 골든 샘플에 끝세로줄이 없어 드러나지 않았던 경우다

### ② 한글 작성자가 깨짐

목록 카드에 `ì€—ìŸ‹ìŽ—`. 기기에서 파일을 가져와 원본 바이트를 봤다:

```
/Author (\xEC\xA0\x84\xEC\x98\x88\xEC\x99\x84)   ← "전예완" 의 UTF-8, BOM 없음
```

PDF 텍스트 문자열은 PDFDocEncoding 이거나 BOM 붙은 UTF-16BE 여야 한다. Microsoft Print to PDF 가 규격을 어기고
UTF-8 을 그대로 썼고, PdfBox 는 규격대로 PDFDocEncoding 으로 읽었다(`pdfinfo` 도 똑같이 깨진다).

- 수정: `PdfDocumentInfo.decodeMisencodedUtf8` — 원본 바이트가 **BOM 없음 + 비ASCII 포함 + 엄격한 UTF-8 로 끝까지 해석**되면
  UTF-8 로 읽는다. 라틴 문자 PDFDocEncoding("Café" 의 E9 단독)은 UTF-8 로 해석되지 않아 그대로 둔다
- **이미 깨진 채 저장된 값**: DB **v8 마이그레이션**이 `docInfoReadAt` 을 비워 다음 목록 로드에서 한 번씩 다시 읽게 한다.
  스키마 변경 없는 데이터 마이그레이션이다. 시각 비교(`docInfoReadAt < 수정 시각`)는 기기 시계에 기대야 해서 택하지 않았다
  (로컬 API 29 에뮬레이터 시계가 실제로 두 달 틀려 있었다)

### 확인

두 수정 모두 **기기에서 가져온 `몰다우.pdf` 로 임시 계측 테스트**를 돌려 확인했다: 작성자 `전예완`, 마디 63개.
사용자 파일이라 저장소에 넣지 않고 지웠다. 회귀 테스트는 합성 데이터로:

- `StaffSystemDetectorTest.끝세로줄은_가짜_마디를_만들지_않는다`
- `PdfDocumentInfoTest` UTF-8 판정 3개, `PdfMetadataReaderTest.BOM_없는_UTF8_작성자를_복구한다` (8진 이스케이프로 원본 바이트 재현)
- `MusicDatabaseMigrationTest.v7_에서_v8_은_…` — 처음에 v3 용 INSERT(8컬럼)를 v7 테이블(10컬럼)에 써서 실패했다. 테스트 쪽 실수였다

## 8. 남은 것

- **박자표 읽기** — 다음 작업. `pdftotext` 로 보니 Moldau 의 "6/8" 은 **텍스트**다(보표마다 6·8 이 위아래, 유니코드 매핑 있음).
  해석기가 보표 안의 숫자 글리프 쌍을 모으면 된다. 메트로놈이 현재 마디를 세는 데 필요하다
- release 빌드 계측 테스트: `androidx.tracing` keep 규칙이 필요하다 (docs/4 §4-5)
- CI release 스모크의 문서 정보 검사는 여전히 모든 매트릭스에서 건너뛴다 (#047 §5)
- PdfBox 엔진의 실기기 수치는 없다
