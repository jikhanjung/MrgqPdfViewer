## 0. 요약

지휘자가 메트로놈(악보 연동 포함)을 시작하면 **연결된 연주자 기기도 같은 박 · 같은 마디 · 같은 페이지로 따라간다.**
일시정지 · 이어서 · 마디 골라 다시 · 정지 · 템포 변경도 따라간다.

**핵심은 "신호가 오면 움직인다"가 아니라 "모두가 같은 시간표를 들고 각자 시계로 읽는다"이다.**

```
지휘자                                              연주자
  │  (연결 직후부터 계속)  clock_ping ◀──────────────  t0
  │                       clock_pong ──────────────▶  t3   → 시계 차이(offset) 추정, RTT 최소 표본
  │
  │  시작: "박 0 = 지휘자 시계 T0 (= 지금 + 1.5초), 120 BPM, 6/8, 12번 마디부터"
  │  metronome_run ─────────────────────────────────▶ 박 k 의 내 시계 시각 = T0 + k·주기 − offset
  │                                                   → 박 표시 · 현재 마디 · 넘김을 각자 계산
  ▼ T0: 둘 다 예비박 1 ────────────── 같은 순간 ─────── ▼
```

사용자 결정 (2026-09-26):
- **연주자 기기 소리는 기본 끔**, 설정(협업 모드 → 합주 메트로놈 소리)으로 켠다. 소리의 기준은 지휘자 기기 하나
- **연주자가 자기 리모컨으로 ↑ · 뒤로를 누르면 그 기기만 빠진다.** 메뉴에서 "지휘자 연주에 다시 합류"로 지금 연주 중인 마디로 돌아온다
- 실측: Z18TV Pro 두 대

## 1. 왜 Phase 0(`turn_at`, 벽시계) 방식을 쓰지 않나

| | Phase 0 (#038) | 이번 |
|---|---|---|
| 공유 시각 | `System.currentTimeMillis()` — 기기 NTP 동기에 의존 (수십~수백 ms 어긋남) | **직접 측정한 offset** (LAN 에서 1~3 ms) |
| 수동 넘김의 지연 | 누를 때마다 lead(2초) 기다림 → 돌발 대처 불가 (보류 사유) | 해당 없음 — 메트로놈 연주는 **미래가 이미 정해져 있다** |
| 넘김 주체 | 지휘자 신호 | **각 기기가 마디로 스스로** (표시 모드가 달라도 맞는다) |

메트로놈 연주는 템포가 일정해 "박 k 가 언제인가"가 시작 순간에 모두 정해진다. 그래서 lead 비용은 **시작 때 한 번(1.5초, 어차피 예비박 전 준비 시간)** 뿐이다.
P03 부록 B 의 오프셋 측정을 여기서 처음 도입한다.

## 2. "현재 마디 표시가 정말 같이 바뀌나" — 오차 예산

현재 마디는 **박 경계에서** 바뀐다. 박 k 의 시각은 모든 기기가 같은 식으로 계산하므로, 기기 간 차이는 아래 항목의 합이다.

| 원인 | 크기 | 대책 |
|---|---|---|
| 시계 offset 추정 오차 | 1~3 ms (같은 Wi-Fi, RTT 최소 표본) | 핑 8회로 시작, 이후 2초마다 1회. 최근 16개 중 RTT 최소 표본 사용 |
| 시계 드리프트 (수정 발진기 20~50 ppm) | 2초에 0.1 ms 미만 | 주기적 재측정. offset 변화는 조금씩 반영(박이 튀지 않게) |
| 화면 갱신 주기 | 한 프레임 이내 (60 Hz 면 ≤ 16.7 ms) | `postOnAnimation` 으로 매 프레임 확인 (기존과 같음) |
| 메시지 전달 지연 | **영향 없음** | 시작은 1.5초 뒤로 예약. 늦게 도착하면 "지금 몇 번째 박인가"를 계산해 그 자리로 합류 |
| 페이지 렌더 (캐시 미스) | 넘김만 늦어짐, 마디 표시는 무관 | 넘김은 원래 2박 전에 미리 (#050). 프리렌더 캐시 |
| **모니터 표시 지연 (HDMI 입력 지연)** | 모니터마다 수십 ms 가능 — **앱 밖** | 같은 모델이면 비슷함. 필요하면 기기별 "화면 지연 보정(ms)" 추가 (§7) |

→ 앱이 만드는 차이는 **대략 20 ms 이내**가 목표다. 사람이 두 화면의 변화를 "동시"로 느끼는 한계(수십 ms)보다 작다.

**화면은 소리가 아니라 시간표를 따른다.** 단독 메트로놈은 박 표시를 AudioTrack 재생 위치로 골랐는데(#047), 합주에서는
소리를 안 내는 연주자도 있으므로 박 표시 · 현재 마디는 **시간표(단조 시계)** 로 고른다. 소리는 그 시간표에 맞춰 놓는다(§4.3).

### 측정 방법 (실기기)
1. **로그 대조** — 두 기기 모두 박이 바뀌어 화면에 반영한 순간을 **지휘자 시계로 환산해** 찍는다
   (`EnsembleSync: beat=… measure=… shownAt(conductor)=…`). 같은 박의 두 값의 차 = 앱이 만든 오차(모니터 지연 제외)
2. **촬영** — 두 화면을 한 프레임에 담아(가능하면 고속 촬영) 현재 마디 박스가 바뀌는 프레임 차이 = 모니터 지연 포함 오차

## 3. 프로토콜

`CollaborationProtocol` 에 추가 (하위호환: 모르는 액션은 구버전이 무시한다 — 기존 계약).

### 3.1 시계 동기 (연주자 → 지휘자 → 연주자)
```json
{"action":"clock_ping","t0":123456789000}                          // 연주자 단조 시계(ns)
{"action":"clock_pong","t0":123456789000,"server_ns":987654321000}  // 지휘자가 받은 순간의 단조 시계(ns)
```
연주자는 받은 순간 `t3` 로 `rtt = t3 − t0`, `offset = server_ns − (t0 + t3)/2` (지휘자 시계 − 내 시계).
- 시계는 양쪽 모두 `System.nanoTime()` (CLOCK_MONOTONIC). `AudioTimestamp.nanoTime` 과 같은 시간축이라 소리 맞추기에 그대로 쓴다
- 지휘자는 받는 즉시 답한다 (파싱 전에 시각부터 잡는다)
- 연결 직후 8회(100 ms 간격), 이후 2초마다. 최근 16개 중 RTT 가 가장 작은 표본의 offset 을 쓴다 (Wi-Fi 지연 튐 제거)

### 3.2 연주 상태 (지휘자 → 연주자)
```json
{"action":"metronome_run","run_id":"r-1727330000-3","file":"Moldau.pdf",
 "state":"playing",                      // playing | paused | stopped
 "anchor_beat":0, "anchor_ns":987655821000,   // 박 anchor_beat 이 지휘자 시계 anchor_ns 에
 "bpm":72, "num":6, "den":8, "dotted":true,
 "start_measure":12,                     // 악보 연동이면 시작 마디, 일반 메트로놈이면 없음
 "paused_measure":null}                  // paused 일 때 멈춘 마디
```
- **상태 전체를 매번 보낸다** (변경분이 아니라). 늦게 들어온 연주자 · 재연결 · 다시 합류가 같은 메시지 하나로 해결된다
- 지휘자는 상태가 바뀔 때, 연주자가 연결될 때, 그리고 연주 중 5초마다 보낸다(유실 대비)
- `run_id` 가 같고 내용이 같으면 무시 (반복 수신 무해)
- 템포 변경(일반 메트로놈에서 연주 중 설정 변경)은 `anchor_beat` = 다음 박으로 새 시간표. 악보 연동은 템포를 바꾸려면 일시정지를 거치므로(#053) 시간표가 하나다
- 시작: 지휘자가 `anchor_ns = 지금 + 1.5초`, 자신도 그 시각에 예비박 시작

박 k 의 시각(지휘자 시계) = `anchor_ns + (k − anchor_beat) × 60e9 / bpm`.

## 4. 구조

### 4.1 순수 로직 (JVM 단위 테스트)
| 파일 | 역할 |
|---|---|
| `ensemble/ClockSync.kt` | 핑 표본 → offset 추정 (RTT 최소, 창, 천천히 반영) |
| `ensemble/BeatTimeline.kt` | 시간표: 박 k ↔ 시각, "지금 몇 번째 박" (지휘자 시계 → 내 시계 변환 포함) |
| `ensemble/EnsembleRun.kt` | `metronome_run` 메시지 ↔ 데이터, 같은 상태 판정 |

### 4.2 네트워크
- `CollaborationServerManager`: `clock_ping` 즉시 응답, `broadcastMetronomeRun`
- `CollaborationClientManager`: 핑 루프, `clock_pong` → `ClockSync`, `metronome_run` → 콜백
- `GlobalCollaborationManager`: 콜백 · 브로드캐스트 전달

### 4.3 메트로놈 엔진 — 시간표 모드
`MetronomeEngine.startScheduled(timeline)` 추가. 단독 메트로놈의 `start()` 는 그대로 둔다.
- 오디오 스레드가 다음 박의 **시각**을 시간표에서 받고, `AudioTrack.getTimestamp()`(프레임 ↔ 단조 시계 대응)로 **몇 번째 프레임에 놓을지** 계산
- 타임스탬프를 250 ms 마다 새로 읽어 오디오 장치 시계와 시스템 시계의 속도 차도 따라간다
- 이미 지난 박(늦은 합류)은 건너뛰고 다음 박부터
- 소리를 끈 연주자는 AudioTrack 없이 돈다 (화면은 어차피 시간표를 따른다)
- 지휘자도 합주 중에는 이 모드로 돈다 (offset 0) — 지휘자 소리 · 화면 · 연주자 화면이 모두 같은 시간표

### 4.4 뷰어 (`PdfViewerActivity`)
- 지휘자: 시작 · 일시정지 · 이어서 · 정지 · 설정 변경 때 `metronome_run` 브로드캐스트. 연주자 연결 시 현재 상태 전송
- 연주자: `metronome_run` 을 받으면 그 파일이 열려 있을 때 악보 분석(캐시) → `ScoreFollower`(같은 시작 마디 · 점음표 박) →
  시간표 모드로 시작. **연동 중에는 지휘자의 `page_change` 를 무시**하고 마디로 스스로 넘긴다 (지휘자와 표시 모드가 달라도 맞다)
- 연주자 ↑ · 뒤로: 그 기기만 빠짐 → 메뉴 "지휘자 연주에 다시 합류" / "이 기기만 정지". 빠진 동안에는 `page_change` 를 다시 따른다
- 지휘자 일시정지: 연주자도 멈추고 멈춘 마디를 파란 상자로 (메뉴는 뜨지 않음 — 고르는 건 지휘자)

## 5. 경계 상황
| 상황 | 처리 |
|---|---|
| 연주자가 다른 파일을 보고 있음 | 무시. 지휘자가 파일을 바꾸면(`file_change`) 열리고, 5초 안에 오는 상태 메시지로 합류 |
| 연주자 악보 분석 실패 · 시작 마디 없음 | 일반 메트로놈(박 표시만)으로 따라감 + 안내 |
| offset 표본이 아직 없음 | 시계 동기 전에는 따라가지 않고 "시계 맞추는 중" — 보통 1초 안에 끝난다 |
| 연결 끊김 | 연주자는 **시간표대로 계속** 간다 (템포가 일정하니 틀리지 않는다). 재연결 시 상태 메시지로 보정 |
| 구버전 연주자 | `metronome_run` 을 모른다 → 지금처럼 `page_change` 로만 따라간다 |
| 지휘자 동기 페이지 넘김(Phase 0) ON | 연주 중 자동 넘김은 기존처럼 즉시 브로드캐스트(연동 중인 연주자는 무시) |

## 6. 테스트 계획
- 단위: `ClockSync`(대칭 · 비대칭 지연, 튀는 표본 무시, 천천히 반영), `BeatTimeline`(박 ↔ 시각, 템포 변경 이어 붙이기, 늦은 합류), `EnsembleRun` 라운드트립
- 실기기(Z18TV Pro × 2): §2 측정 방법. 시작 · 일시정지 · 이어서 · 다른 마디 · 정지 · 연주자 빠졌다 합류 · 연주 중 연주자 재연결

## 6-1. 구현 후 결정 · 실측 (2026-09-26)

**실측 (Z18TV Pro × 2, 지휘자 .75 · 연주자 .47, 몰다우 60 BPM)** — 두 기기 `EnsembleSync` 로그에서 같은 마디 35쌍:
- 마디가 바뀐 시각(지휘자 시계 환산) 차이 **중앙값 −2.5 ms**(연주자가 약간 먼저), 35번 중 4번 +13~14 ms
- 튀는 값은 **화면 갱신 한 프레임**(60 Hz = 16.7 ms): 두 기기의 vsync 위상이 달라 박 시각이 그 사이에 걸리면 한쪽이 한 프레임 늦게 그린다.
  `late`(박 시각 대비 반영 지연)가 양쪽 모두 0~17 ms 톱니로 도는 것이 그 흔적 → 앱이 만드는 차이는 **최대 한 프레임, 보통 3 ms 이내**
- 시계 동기 RTT 6 ms 안팎 (첫 표본 57 ms 는 최소 RTT 선택으로 걸러짐). 20번 마디부터 다시 시작해도 연주자가 바로 합류

**사용자 추가 요청**
- **지휘자가 마디를 고를 때도 동기화**: 상태 `selecting` + `focus_measure`(지휘자 커서). 연주자는 그 마디에 파란 상자, 그 페이지로 넘김.
  커서는 보기만 한다. 일시정지(`paused`)도 같은 `focus_measure` 로 멈춘 마디를 보인다. 처음 시작할 때 고르는 것도 같다
- **연주자의 메트로놈 설정은 소리 켜기/끄기만** — 나머지는 지휘자를 따른다. 따라가는 중에 바꾸면 같은 시간표로 엔진만 다시 시작해 박이 그대로 이어진다
- 그에 맞춰 연주자 조작을 다시 정했다: **↑ 는 메뉴만** 연다(이 기기만 빠지기 / 다시 합류 / 메트로놈 설정(소리)) — 설정을 열려고 빠질 필요가
  없게. **뒤로**는 여전히 그 기기만 빠진다. **OK 길게**(PDF 표시 옵션)는 연주자면 멈추지 않는다. 연주자 모드에서는 혼자 메트로놈을 시작하지 않는다

**그 밖에**
- 서버 `SimpleWebSocketConnection.sendMessage` 에 동기화 — 브로드캐스트 스레드와 읽기 스레드(clock_pong)가 동시에 쓰면 프레임이 섞일 수 있었다 (기존 결함)
- 시간표 모드에서 `getTimestamp()` 를 1초 넘게 못 얻으면 재생 위치로 대신한다 (타임스탬프를 안 주는 장치 대비)
- 지휘자가 일시정지한 동안에는 연주자도 지휘자의 수동 넘김(`page_change`)을 따른다. 따라가는 중 · 마디 고르는 중에는 무시

## 7. 나중에
- 기기별 **화면 지연 보정**(ms) — 모니터가 달라 눈에 띄게 어긋나면
- 소리 켠 연주자의 **오디오 지연 보정** — HDMI 스피커 지연은 `getTimestamp` 에 안 잡힌다
