## 1. 설계 — 왜 AudioTrack 인가

흔한 구현은 Handler/코루틴 타이머로 박마다 SoundPool 을 울리는 것이다. 이러면 스레드 스케줄링에 따라
**박마다 수~수십 ms 씩 흔들린다.** 연주자가 듣는 메트로놈에서 그 흔들림은 바로 들린다.

그래서 **AudioTrack 스트림에 클릭 파형을 직접 이어 쓴다.** 박이 스트림의 몇 번째 샘플에서 시작하는지를
계산으로 정하므로, 스레드가 늦게 깨어나도 박 간격은 샘플 단위로 정확하다.

```
MetronomeClock (순수) ── 다음 박의 프레임 위치 ──┐
ClickSynth (순수)     ── 클릭 파형 ─────────────┤
                                               ▼
MetronomeEngine ── 512프레임씩 채워 AudioTrack.write (블로킹이 속도를 맞춘다)
       │
       └─ currentBeat(): playbackHeadPosition(실제 재생 위치)를 지난 가장 최근 박
              ▼
MetronomeBeatView ── postOnAnimation 으로 매 프레임 갱신 (바뀔 때만 다시 그림)
```

| 파일 | 역할 | 테스트 |
|---|---|---|
| `metronome/MetronomeClock.kt` | 박 위치(샘플), 강박, 템포·박자 변경 규칙 | JVM 7 |
| `metronome/ClickSynth.kt` | 35ms 사인 + 빠른 감쇠, 첫 박 A6·나머지 D6 | JVM 3 |
| `metronome/MetronomeEngine.kt` | AudioTrack 스트림, 무음 폴백 | 에뮬레이터 (§4) |
| `metronome/MetronomeBeatView.kt` | 박 표시 | 스크린샷 |

### 규칙

- **누적 오차 없음**: 박 간격을 실수로 누적하고 박마다 반올림한다. 97 BPM(박당 27278.35… 프레임)을
  정수로 잘라 누적하면 1000박 뒤 350프레임(8ms) 밀린다 — 테스트로 고정
- **템포·박자 변경은 다음 박부터**: 이미 놓인 박을 옮기지 않으니 연주 중 조절해도 박이 튀지 않는다.
  반영까지 최대 1박 + 한 번 쓰는 양(512프레임 ≈ 12ms)
- **박자를 줄여 마디를 넘으면 새 마디 첫 박부터**
- **첫 박 앞 0.15초 여유**: 재생 시작 직후 클릭 앞머리가 잘리지 않게
- **클릭 앞 1ms 서서히 올림**: 파형이 0 에서 시작해 "딱" 잡음이 없다
- **소리와 표시가 같은 시계**: 표시는 `playbackHeadPosition` 으로 고른다 — 쓴 위치가 아니라 들리는 위치
- **소리 장치를 못 열면 무음 모드**: 벽시계로 박만 센다. "박 표시만 합니다" 토스트

### 멈추는 때

- 뷰어가 `onPause` 될 때 (홈·다른 앱으로 가도 계속 울리지 않게)
- **다른 곡으로 넘어갈 때** — 템포가 파일별이라 이전 곡 템포로 계속 도는 건 틀린 동작이다

## 2. 저장 (스키마 v7)

`user_preferences.metronomeBpm`, `metronomeBeatsPerBar` (둘 다 INTEGER, nullable).

- **null = 미설정** → 기본값(120 BPM, 4박). 나중에 **MusicXML 의 템포·박자표로 채울 자리**이기도 하다
- 저장은 `updateMetronome` 부분 UPDATE 로만 — 행 전체를 다시 쓰지 않는다
- 템포·박자는 대화상자를 닫을 때 저장한다. 클릭음 켜기·음량은 전역 설정(SharedPreferences)

### 확인한 우려

클리핑·여백 저장 코드(`saveClippingSettings`, `savePaddingSettings`)가 `insertUserPreference`(REPLACE)를 쓰는 것을
보고 "저장할 때마다 메트로놈 값이 지워진다"고 먼저 판단했는데, **끝까지 읽어 보니 아니었다.** 행이 있으면
`currentPrefs.copy(...)` 로 만들어 새 컬럼이 보존되고, 새 객체는 행이 없을 때만 만든다(잃을 값이 없다).
`user_preferences` 에는 하위 테이블이 없어 REPLACE 로 연쇄 삭제도 없다. 보존 동작은 `MusicDatabaseTest` 에 테스트로 넣었다.

## 4. 에뮬레이터 확인 (API 29 TV, **오디오 켠 상태**)

adb 로는 확인이 막혔다:
- `sendevent` 로 OK 길게 누르기 → **Permission denied** (`user` 빌드, 루트 불가)
- `input keyevent --longpress` → 누른 채 기다리지 않아 앱의 800ms 기준에 못 미침
  (`long_press_timeout` 을 1500 으로 올려 봤지만 효과 없음 — 원래 값 400 으로 되돌렸다)

그래서 **커밋하지 않는 임시 계측 테스트**로 확인하고 지웠다. 같은 프로세스라 키 down/up 사이에 1.1초를
둘 수 있고, 대화상자 목록 포커스 위치를 알 수 없어 메트로놈 대화상자·시작·정지는 뷰어 메서드를 직접 불렀다.

| 확인 | 결과 |
|---|---|
| OK 1.1초 → 옵션 메뉴 | "메트로놈" 항목 표시 ✓ |
| 메트로놈 대화상자 | 템포 120·버튼·박자 4·클릭음·음량 ✓ |
| 100 BPM, 3박 시작 | `silent=false` — **AudioTrack 소리 모드** |
| 박이 재생 위치로 넘어가나 | 박 프레임 59535 → 85995 → 112455 → 138915: **간격 26460 = 44100×60/100 정확**, 박 번호 2→0→1→2 |
| 화면 | 왼쪽 위 `♩ 100`, 3박째 초록 → 첫 박 주황 (두 시점 스크린샷) |
| 정지 | `running=false`, 박 표시 사라짐 ✓ |

확인하지 **못한** 것:
- **귀로 들어 보지 않았다.** 에뮬레이터 오디오가 호스트로 나왔는지, 실제 지연·음색은 모른다
- 대화상자의 버튼·슬라이더를 리모컨으로 조작하지 않았다 (메서드 직접 호출)
- 저장한 템포가 파일을 다시 열었을 때 대화상자에 채워지는지 UI 로는 안 봤다 (DAO 테스트만)
- 실기기 (Google TV Streamer + 모니터 스피커/HDMI 오디오 지연)

## 5. CI 에서 드러난 것 — 문서 정보 스모크는 CI 에서 한 번도 돌지 않는다

`f154262`(046) 의 CI 는 Build·Instrumentation(API 21/30/34) 모두 **초록불**이다. 그런데 매트릭스 로그를 보면
release 스모크의 문서 정보 검사는 **세 곳 모두 건너뛰었다**:

| API | 넣기 | 앱 로그 | 판정 |
|---|---|---|---|
| 21 | 실패 코드 | `LOADED 0 PDF FILES` | 경고, 건너뜀 |
| 30 | 실패 코드 | `LOADED 0 PDF FILES` | 경고, 건너뜀 |
| 34 | 성공 코드 | `LOADED 0 PDF FILES` | 경고, 건너뜀 |

셸이 넣은 파일을 **앱이 어느 CI 이미지에서도 보지 못한다.** a7eb7f6 의 판정 로직은 의도대로 "배치 문제"로
분류해 CI 를 빨갛게 만들지 않았지만, 그 결과 **minify 된 release APK 에서 PdfBox 가 도는지는 로컬 API 29
에서만 확인된 상태**다. 초록불이 검증을 뜻하지 않는다 — 043 의 "게이트를 켠 것과 게이트가 도는 것은 다르다"가 다시 나왔다.

고치는 길(아직 안 함):
- `connectedReleaseAndroidTest` — 테스트가 앱 프로세스 안에서 샘플을 직접 쓰면 배치 문제가 사라진다
  (docs/4 §4 의 5번 항목과 같은 일)
- 또는 스모크가 **모든 매트릭스에서 건너뛰면 실패**하도록 (최소 한 곳은 돌아야 한다)
