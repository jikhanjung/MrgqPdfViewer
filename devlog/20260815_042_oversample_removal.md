## 0. 요약

> "PDF 렌더링이 나아지긴 했지만, 어도비 리더가 1920×1080 모니터에서 그려주는 또렷한 선과는
> 여전히 비교가 된다."

이 관찰이 출발점이었다. 배율 스윕을 돌려보니 원인이 명확했다 — **oversample 자체가 원인**이다.

| oversample | darkness 평균 | 최소 | 표준편차 | 두께 표준편차 |
|---|---|---|---|---|
| **1.0× (네이티브)** | **1.000** | **1.000** | **0.000** | **0.310** |
| 1.5× | 0.827 | 0.669 | 0.101 | 0.529 |
| 2.0× | 0.661 | 0.504 | 0.122 | 0.539 |
| 2.5× (v0.1.11) | 0.635 | 0.407 | 0.119 | 0.500 |
| 4.0× (v0.1.12) | 0.674 | 0.504 | 0.102 | 0.520 |
| 4.0× + 감마 2.0 (#041) | 0.878 | 0.754 | 0.074 | 0.492 |

**1× 에서는 오선 50개가 전부 순수 검정이고 편차가 0.000 이다.** 두께 편차도 1× 가 가장 낮다.
즉 모든 지표에서 1× 가 이긴다. 어도비가 또렷한 이유가 이것이고, 우리가 흐렸던 이유도 이것이다.

## 1. 왜 이렇게 되나

PDFium(= Android `PdfRenderer` 의 내부 엔진)은 **1픽셀 미만 stroke 를 device pixel 에 스냅**한다.
데스크톱 뷰어가 저해상도에서도 얇은 선을 또렷하게 그리는 바로 그 동작이다.

- **1×**: A4 악보의 오선(≈0.5pt × fitScale 1.283 ≈ 0.64px)이 **정확히 1px 검정**으로 스냅된다.
- **N×**: 스냅은 렌더 해상도 기준이라 여전히 1px 이지만, 그것을 1/N 로 다운스케일하면
  표시 기준 **1/N 픽셀 분량의 잉크**가 되어 회색으로 희석된다.

**oversample 을 올릴수록 얇은 선은 흐려진다.** supersampling 이 유리한 것은 출력 해상도가
렌더 해상도보다 높거나 aliasing 이 심한 콘텐츠일 때인데, 악보는 정반대 조건이다.

## 2. 어쩌다 이 길로 들어섰나 (기록)

세 단계가 각각은 합리적이었는데 합치니 잘못된 방향이었다.

1. **P01 (v0.1.11)**: 두 페이지 모드의 오선 두께 불균일. 진짜 원인은 **2단계 fractional
   scaling**(렌더 → 비트맵 스케일 → ImageView fit)이었고, 이를 단일 Matrix 렌더로 고쳤다.
   **이때 oversample 2.5× 를 함께 도입했는데, 그 독립적 기여는 검증된 적이 없다.**
2. **P2 (v0.1.12)**: 특정 오선만 회색이 되는 dropout → 2.5× → **4×** 로 상향. 실제로
   0.635 → 0.674 로 나아지긴 했다(위 표). 하지만 **반대 방향으로 갔으면 1.000 이었다.**
3. **#041 (2026-08-15)**: 희석된 잉크를 감마로 사후 보정 → 0.878. 여전히 1.000 에 못 미치고,
   중간톤을 통째로 어둡게 하는 방식이라 선이 두껍고 물러 보인다.

근본 전제는 **"2.5K/4K 화면에서 해상도를 최대한 활용하자"** 였다. 그런데 [#040](20260815_040_4k_display_investigation.md)
에서 **앱 UI 가 1080p 로 고정**돼 있음이 확인되면서 그 전제가 사라졌다. 출력이 표시 해상도에
묶여 있으면 supersampling 은 이득이 없고 손해만 남는다.

## 3. 구현

### 3-1. oversample 기본값 4.0 → 1.0, 런타임 조정 가능

`PageCache.OVERSAMPLE_FACTOR`(const) → `DEFAULT_OVERSAMPLE_FACTOR = 1.0f` +
`@Volatile var oversampleFactor`. `effectiveOversampleFactor()` 는 1× 면 즉시 반환하고,
2× 이상일 때만 기존 34MP 상한 로직을 탄다. 1× 에서는 `createScaledBitmap` 이 같은 크기를
받아 원본을 그대로 돌려주므로 **다운스케일 단계가 통째로 no-op** 이 된다(비용도 절감).

### 3-2. 감마는 oversample 에 종속 — 1× 면 자동으로 꺼짐

`InkGamma.defaultFor(screenHeight, oversample)` 로 시그니처 확장. 감마는 oversample 이
만든 희석을 되돌리는 보정이므로 **1× 에서는 존재 이유가 없다**(오선이 이미 순수 검정).
이때 감마를 걸면 중간톤만 어두워져 음표·슬러가 무거워진다. → `oversample <= 1.001f` 면 `MIN`(1.0).

### 3-3. ⚠️ 정수 좌표 — 이게 없으면 1× 가 무의미하다

1× 의 선명함은 비트맵이 **정수 좌표에 1:1 로 놓일 때만** 유지된다. 소수점 좌표로 blit 하거나
1.0 이 아닌 배율로 그리면 재샘플링돼 device-pixel 스냅이 도로 뭉개진다. 두 곳을 고쳤다:

- `combineTwoPagesUnified`: `leftX/leftY/rightX/rightY` 가 `/2f` 로 소수점이 될 수 있었다
  (중앙 여백이 홀수일 때). 정수 나눗셈 후 `toFloat()` 으로 변경.
- `setImageViewMatrix`: `dx/dy` 를 정수로 반올림. 추가로 **scale 이 1.0 에 극히 가까우면
  정확히 1.0 으로 스냅**(0.999… 배율은 비트맵 전체를 재샘플링시킨다).

### 3-4. 설정 UI 통합

"오선 진하기 (감마)" → **"선 선명도 (배율 · 감마)"** 로 확장. 슬라이더 2개(배율 1.0~4.0
0.5단위 / 감마 1.0~3.0 0.05단위), 빠른 버튼 `권장 1×` · `이전 4×+γ2`, 실시간 미리보기.
두 값 모두 전역 설정(SharedPreferences `oversample_factor`, `ink_gamma`).

## 4. 남은 확인 (실기기)

- [ ] **1× vs 4×+γ2 육안 A/B** — "권장 1×" / "이전 4×+γ2" 버튼으로 즉시 전환 가능
- [ ] **곡선(슬러·크레센도) 확인** — 1× 는 PDFium 자체 AA 만 쓴다. 오선은 확실히 이기지만
      곡선이 supersampling 대비 거칠어 보이는지가 유일한 리스크
- [ ] **두 페이지 모드** — 정수 좌표 수정이 실제로 선명도를 지키는지 (여기가 P01 의 원래 무대)
- [ ] **렌더 속도** — 13.2MP → 0.83MP 로 **약 16배 감소**. 페이지 전환·캐시 미스가 빨라져야 정상
- [ ] **메모리** — transient oversample 비트맵(~133MB)이 사라진다

## 5. 교훈

P01 에서 oversample 을 도입할 때 **2단계 scaling 제거와 묶어서 한꺼번에** 넣었기 때문에,
어느 쪽이 효과를 냈는지 분리되지 않았다. 이후 P2 는 그 미검증 전제 위에서 배율만 올렸고,
#041 은 그 부작용을 사후 보정했다. **한 번에 한 변수만 바꿨더라면** 2.5× 도입 시점에
1× 와의 비교로 끝났을 문제다.
