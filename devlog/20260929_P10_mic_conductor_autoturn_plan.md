# P10 — 태블릿 지휘자가 연주를 듣고 쪽을 넘기기 (마이크 자동 넘김 · 연주자 차례 넘김)

작성일: 2026-09-29
상태: 🟢 **구현 · 아르페지오네 실기기 확인 끝**(§8 · §9 · §11) — 태블릿 지휘자 + Z18TV 연주자. 시작 찾기 뒤 세 번째 시험: 처음 40초 ±1마디 100%, 전체 93%, 쪽 넘김 ±2초 91%. **다음: 여러 곡 시험**(§12)

## 0. 한 줄

**태블릿이 지휘자**가 되어 마이크로 연주를 들으며 **지금 치고 있다고 보는 쪽**을 보여 주고 스스로 넘긴다.
넘길 때마다 연주자에게 `page_change` 를 보내고, **두 쪽으로 보는 연주자(TV)** 는 조금 기다렸다가 **다 친 쪽 자리만** 다음 쪽으로 바꾼다(차례 넘김).

## 1. 왜 이렇게 (P08 결과)

- 아르페지오네 1악장 실제 연주(915초)에서 온라인 추적은 ±1마디 안 90%, **쪽 끝 + 1초 머무름** 규칙이면 27번 넘김이 모두 ±1.2마디(−3.7 ~ +2.1초) 안 (P08 §7-2)
- 일찍 넘기는 것이 위험하다(치던 마디가 사라짐). 늦게 넘기는 것은 몇 초 불편할 뿐 → **늦게 쪽으로 기운 규칙**
- 두 쪽 화면에서 다 친 쪽만 바꾸면 여유가 약 반 쪽(≈ 5마디 ≈ 15초) — 추적 오차가 그 안에 든다

## 2. 사용 장면

1. 태블릿(지휘자): 곡을 열고 ↑ 메뉴(두 번 탭) → **🎤 연주 듣고 넘기기** → 지금 쪽 첫 마디부터 듣기 시작(첫 소리가 날 때까지 기다림)
2. 태블릿 화면: 세로 한 쪽을 **반 쪽씩 넘긴다** — 추정 위치가 쪽 **아래 절반**에 들어서면 **위 절반만** 다음 쪽의 위 절반으로 바꾼다(아래 절반은 치는 중이라 그대로). 쪽 끝을 지나 1초 머무르면 아래 절반도 다음 쪽 → 온전히 다음 쪽. 오른쪽 위에 🎤 와 추정 마디(예: `🎤 37`)
3. 연주자(TV, 두 쪽): 처음엔 1 | 2. 지휘자가 2쪽에 들어서면 몇 초 뒤 왼쪽만 3 → **3 | 2**. 지휘자가 3쪽에 들어서면 몇 초 뒤 오른쪽만 4 → **3 | 4**. 늘 "지금 치는 쪽 + 다음 쪽"이 보인다
   - 사람의 넘김 동작을 흉내 낼 필요는 없다(사용자, 2026-09-29): **TV 는 다 친 쪽 하나를 그 쪽 + 2 로 바꾸고, 태블릿은 아래를 칠 때 위만 다음 쪽 위로 바꾼다**
4. 틀렸을 때: 지휘자가 손으로 넘기면(탭 · 페달) 추적기가 그 쪽 첫 마디로 다시 맞춘다. 연주자 쪽은 그 신호대로 따라간다
5. 끝: 메뉴에서 멈춤, 화면을 떠나면 멈춤, 마지막 쪽 끝이면 멈춤

## 3. 설계

### 3.1 지휘자 — 마이크 악보 추적기 (`follow/` 새 패키지, 순수 Kotlin 은 JVM 단위 테스트)

| 부분 | 내용 |
|---|---|
| 소리 받기 | `AudioRecord` 44.1kHz 모노(`UNPROCESSED` → 안 되면 `MIC`, 녹음 도구와 같이). 스레드 하나 |
| 특징 | **STFT 크로마** — 창 4096(≈ 93ms) · 걸음 2048(≈ 46ms) @44.1kHz, 60 ~ 4000Hz 빈을 12음으로(반음 중심 삼각 무게 × **세기**), 벡터 정규화. 0단계에서 CQT 와 비교해 채택(§6) |
| 악보 크로마 | MusicXML(`MusicXmlReader`) 음표 → 마디 시작(4분음표) → 기준 빠르기로 초 → 같은 46ms 칸에 12음 무게(친 뒤 0.6초로 줄어듦). 기준 빠르기 = 그 파일 메트로놈 템포(없으면 곡 기본). 구간별 빠르기는 1차에선 첫 구간만 |
| 정렬 | P08 과 같은 **OLTW**(±3초 띠, D/(i+j) 최소, 앞으로만) + **주기적 재위치**(1초마다 최근 30초를 ±40초 악보에 부분 DTW, 끝 5초로 판정, 1.15배, 평균 빠르기로 후보 고르기). 재위치는 0.25초 칸으로 줄여 계산 |
| 시작 | 시작 마디(지금 쪽 첫 마디)에서, **첫 소리**(짧은 창 음량이 배경보다 충분히 커짐)부터 정렬 시작 |
| 넘김 판단 | **반 쪽 넘김**: 추정 위치가 지금 쪽 **아래 절반 시스템**(시스템 위끝이 쪽 높이 절반 아래)의 첫 마디에 들어서 1초 머무르면 → 위 절반을 다음 쪽 위 절반으로. 추정이 **지금 쪽 마지막 마디 끝**을 넘어 1초 머무르면 → 다음 쪽(= `page_change`). 쪽 · 마디 · 시스템은 악보 분석 마디 지도(`ScoreMeasure.pageIndex` · 좌표) |
| 손으로 넘김 | 추적 중 지휘자가 넘기면 그 쪽 첫 마디로 추적기를 다시 맞춘다(재시작) |
| 기록 | 추적 중 WAV + 사건 JSON(추정 마디 · 넘김 · 재위치)을 `recordings/` 에 — 실제 성적을 나중에 재고 규칙을 다듬는 자료. 소리 받기는 하나로(녹음 버튼과 같은 `AudioRecord` 를 두 번 열지 않는다) |
| 계산량 | 크로마 1프레임(4096 FFT) + OLTW 띠 130칸 ≈ 1ms 미만, 재위치 1초에 한 번 120 × 320 칸 부분 DTW ≈ 수 ms — 스냅드래곤 870 에 충분 |

조건: TV 가 아님 · 마이크 있음 · 그 파일에 **맞는 MusicXML**(`MusicXmlMatch` — 마디 수 · 박자) · 악보 분석 마디 지도 있음 · **전체 악보**(지휘자는 늘 총보). 안 되면 메뉴에 이유를 보여 준다.

### 3.2 합주 신호 — `page_change` 에 `roll` 더하기

- 지휘자는 지금처럼 쪽이 바뀔 때마다 `page_change`(원본 쪽 번호, 1부터)를 보낸다. 마이크 추적으로 넘긴 것이면 **`"roll": true`**
- 옛 연주자 앱은 모르는 키를 무시 → 지금처럼(두 쪽이면 짝 1-2 · 3-4 로) 동작. 하위 호환
- `CollaborationProtocol.buildPageChange` 에 선택 인자, 받는 쪽 콜백에 `roll` 전달

### 3.3 연주자 — 두 쪽 차례 넘김 (`RollingTurns`, 순수 로직 + 뷰어)

- 두 쪽 모드의 **자리 = 쪽 홀짝**: 왼쪽은 늘 홀수 쪽(1 · 3 · 5 …), 오른쪽은 늘 짝수 쪽. 차례 넘김은 한 자리만 바꾼다 → 3 | 2, 3 | 4, 5 | 4 …
- `roll` 이 붙은 쪽 p 를 받으면:
  - **p 가 화면에 있음** → 다른 자리의 쪽 q 가 p 보다 앞이면(다 친 쪽) **D 초 뒤** q 자리를 **p + 1** 로. 뒤면(아직 안 친 쪽) 그대로
  - **p 가 화면에 없음**(건너뜀 · 되돌아감 · 처음) → 지금처럼 **바로** p 가 든 짝(pairStart)으로
  - 새 신호가 오거나 연주자가 손으로 넘기면 기다리던 바꿈은 취소
- **D(기다림) 기본 5초** — 지휘자 넘김이 최악 3.7초 일찍이었다(P08 §7-2) + 마이크 지연. 너무 늦어도 다음 쪽은 반 쪽 치는 동안(≈ 15초) 필요 없으므로 넉넉히. 설정은 2단계에서
- 한 쪽 모드 연주자 · 파트 보기 연주자 · 합주 메트로놈을 따라가는 연주자 → 1차에서는 **지금 동작 그대로**(roll 무시)
- 화면 그리기: `showPage(index)` 는 늘 (index, index + 1) — **임의의 두 쪽**(왼 · 오)을 그리는 길을 더한다. `combineTwoPagesUnified(left, right)` 는 이미 비트맵 둘을 받는다. 캐시 프리렌더는 보이는 두 쪽 + 다음 쪽
- `pageIndex`(지금 쪽)는 **지휘자가 알린 쪽 p** 로 — 쪽 정보 · 마디 박스 · 저장은 그 기준

### 3.3.1 지휘자 화면 — 반 쪽 넘김

- 태블릿(세로 한 쪽)에 **위 절반 · 아래 절반을 다른 쪽에서** 가져와 그리는 길: 위 = 다음 쪽의 위 절반, 아래 = 지금 쪽의 아래 절반, 가운데 가는 구분선
- 자르는 선 = 쪽 높이의 절반 — 악보 분석의 시스템 경계와 맞추면 시스템이 잘리지 않는다(절반에 가장 가까운 시스템 사이 틈). 1차는 시스템 사이 틈
- `pageIndex` 는 아래 절반의 쪽(지금 치는 쪽). 반 쪽 상태에서 손으로 넘기면 온전한 다음 쪽으로

### 3.4 화면 · 메뉴

- 메트로놈 메뉴(↑ · 두 번 탭)에 **🎤 연주 듣고 넘기기** / **🎤 멈춤** (태블릿에서만)
- 오른쪽 위 녹음 버튼 자리 옆에 `🎤 37` (추정 마디), 소리를 기다리는 동안 `🎤 대기`
- 추적 중에는 녹음 버튼을 숨긴다(추적이 녹음도 함께 한다)

## 6. 0단계 결과 — STFT 크로마 (2026-09-29)

앱에서 계산할 STFT 크로마(numpy 로 똑같이 — `data/score_follow_dtw.py stft_chroma`)를 CQT 와 비교. 아르페지오네 1악장, 같은 기준 경로(23ms CQT 로 만들어 저장, `--ref-save/--ref-load`), 넘김 규칙 = 쪽 끝 + 1초 머무름, 27번 넘김.

| 온라인 추적 특징 | ±1마디 안 | ±0.5마디 | 넘김 ±2초 안 | 최악 이름 / 늦음 | 가려짐: 온전한 넘김 / **반 쪽 넘김** |
|---|---|---|---|---|---|
| CQT 23ms (P08 기준) | 90% | 74% | 89% | −3.7 / +2.1초 | 0 / **0** |
| CQT 46ms | 90% | 74% | 93% | −9.1 / +1.9초 | 1 / **0** |
| STFT 세기² 46ms | 86% | 70% | 78% | −8.9 / +3.9초 | 2 / **0** |
| **STFT 세기 46ms (채택)** | 88% | 72% | **93%** | −6.5 / +3.3초 | 1 / **0** |
| STFT 세기² 23ms | 86% | 70% | 78% | −10.3 / +4.1초 | 3 / **0** |
| STFT 세기² 46ms, 130Hz 부터 | 87% | 69% | 74% | −8.8 / +3.9초 | 2 / **0** |
| STFT log(1+100·세기) | 실패(추적이 멈춤) | | | | |

- STFT 는 CQT 보다 조금 못하지만 **반 쪽 넘김이면 어느 쪽이든 가려짐 0** — 지휘자 반 쪽 넘김 · 연주자 차례 넘김 설계에서는 충분하다
- 46ms 칸이 23ms 보다 나쁘지 않다(오히려 약간 낫다) → 계산량도 절반
- 앱이 CQT 로 가야 하는 경우는 기타 녹음(4단계)에서 STFT 가 모자랄 때

## 7. 1단계 결과 — 추적 핵심 (2026-09-29)

`follow/` 패키지 (순수 Kotlin, JVM 단위 테스트 `MicFollowTest`):

| 파일 | 내용 |
|---|---|
| `ChromaExtractor` · `Fft` | 44.1kHz · 4096 · 2048(≈ 46ms) STFT 크로마(세기 무게), 소리를 조금씩 넣으면 칸마다 콜백. 기수 2 반복형 FFT |
| `ScoreChroma` | MusicXML → 같은 칸의 기준 크로마(친 뒤 0.6초로 줄어듦), 마디 시작(박자표로), 칸 ↔ 4분음표 ↔ 연속 마디 위치 |
| `OnlineAligner` | OLTW(±3초 띠) + 주기적 재위치(1초마다 30초 창, ±40초, 끝 5초 판정, 1.15배, 평균 빠르기로 후보) — librosa 부분 DTW 의 걸음 순서 · 되짚기까지 그대로 |
| `PageTurnDecider` | 연속 마디 위치 → 반 쪽 넘김(아래 절반 첫 마디 + 1초) · 쪽 넘김(다음 쪽 마디 + 1초), 손으로 옮김 |

- **Python 과 같은가**: 아르페지오네 1악장(915초, 19,694칸)을 Python 과 같은 입력으로 넣으면 **경로가 칸 단위로 100% 같다, 재위치 70번 = 70번**. 크로마 계산도 60초 구간에서 최대 차이 < 1e-3
  - 처음엔 87% 였다 — Python 경로를 float64 입력으로, Kotlin 은 float32 로 내보낸 입력으로 돌려서. 같은 float32 입력이면 100%
  - 비교 자료는 저장소 밖(`data/recordings/fixtures/` — `score_follow_dtw.py` 로 만듦), 없으면 테스트는 건너뛴다(CI)
- 계산 시간: JVM 에서 915초 녹음 전체가 약 13초(재위치 포함) — 실시간의 70배 빠름

## 8. 2 · 3단계 · 실기기 첫 시험 (2026-09-29)

### 구현

- **지휘자(태블릿)**: ↑ 메뉴(두 번 탭) 맨 위 **🎤 연주 듣고 넘기기 / 듣기 멈춤** (태블릿에서만). 조건을 못 채우면 이유를 알림(연주자 · 파트 보기 · MusicXML 없음 · 마디 없음 · 안 맞음)

## 9. 관성 항법 거르개 · 시스템 표시 (2026-09-29)

사용자 제안: "연주는 대체로 고른 빠르기로 이어진다 — 짧게 헤매는 동안은 그 빠르기로 간다고 보고 보여 주고, 마이크 추정이 다른 곳을 **일정 시간 넘게 일관되게** 가리킬 때만 옮기자. 서버 부하 그래프의 시간 평균 같은 효과". 그리고 지휘자 화면에 지금 마디와 함께 **시스템도 연하게**.

- `follow/InertialTracker` — 예측 x̂ = x + v, 추정 z 가 문(1초 = 악보 칸 21.5) 안이면 α-β 거르개(α 0.15, β 0.002, v 0.5 ~ 2), 밖이면 관성(x = x̂).
  z 가 3초 동안 문 밖에서 고른 빠르기(직선 맞춤 기울기 0.5 ~ 2, 흩어짐이 문 안)로 가면 그쪽으로 옮김. 손으로 넘기면 다시 시작

## 10. 그다음 구상 — 태블릿은 "악장", 지휘자는 TV (2026-09-29, 사용자)

- 지휘자(TV)는 그 위치에서 **중요한 사건만**(쪽 넘김 등) 연주자들에게 전한다 — 넘김 판단(`PageTurnDecider` · 차례 넘김)은 지휘자 쪽으로
- 지금 구조에서 옮기는 것:
  - 추적(`MicScoreFollower` · 정렬 · 관성)은 태블릿에 그대로. 넘김 판단만 지휘자로
  - 새 신호 "악장 → 지휘자": 위치(연속 마디) · 빠르기 · 확신도를 1초에 몇 번. WebSocket 은 이미 양방향(`clock_ping` 이 연주자 → 지휘자) — 합주 역할에 "악장"을 더한다
  - 지휘자 TV 는 받은 위치로 자기 화면(두 쪽)을 차례 넘김하고, 연주자에게 `page_change.roll`
  - 지휘자 TV 의 리모컨 넘김은 늘 우선(사람이 최종 결정)
- **부가 기능(앞 단계가 튼튼해진 뒤)**: 블루투스 페달로 넘김 덮어쓰기, 태블릿에서 마디를 탭해 거기부터 다시 시작
- 미리 생각할 것: 악장 연결이 끊기면(지휘자는 손 넘김으로), 악장이 둘이면(하나만), 지휘자와 악장의 악보 · MusicXML 이 같은 판인지(`sha256`)
