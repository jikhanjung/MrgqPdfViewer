## 1. 조사 — 박자표는 텍스트인가 경로인가

악보 기호가 경로면 OMR 이 필요하고, 텍스트면 위치만 읽으면 된다. `pdffonts`·`pdftotext -bbox` 로 Moldau 를 봤다:

- 글꼴 4개(CID TrueType/Type0C, 유니코드 매핑 있음), 텍스트 연산자는 **59개뿐** (제목, 마디 번호, "pizz." 등)
- 1쪽 첫 시스템 **보표 5개 모두에 "6" 과 "8"** 이 같은 x(106~112pt)에, 보표 높이(19.8pt)의 약 절반(10.3pt) 간격으로 위아래로
- 마디 번호("5", "8", "11")와 운지("0")는 **보표 밖에 혼자**

→ 박자표는 텍스트다. 이 배치를 판정 규칙으로 삼았다.

## 2. 박자표 읽기

### 해석기가 텍스트 위치를 모은다

`PathContentInterpreter` 에 `textSink` 를 주면 텍스트 행렬(`BT Tf Td TD Tm T* TL`)을 따라가며 `Tj`·`TJ`(배열 문자열 이어 붙임)·`'`·`"` 마다
`TextRun(text, x, y, size)` 를 넘긴다. 문자열 해독(리터럴 이스케이프 `\ddd` 등, 16진)은 해석기가, **글리프 코드 → 유니코드는 PdfBox 글꼴**
(`PDResources.getFont` → `readCode` → `toUnicode`, 글꼴 캐시)이 한다. `textSink` 가 없으면 문자열을 해석하지 않아 #049 속도 그대로다.

한계: 한 문자열 안에서 글리프 폭만큼의 이동은 계산하지 않는다 — 위치는 각 텍스트 연산의 시작점.

### `TimeSignatureDetector`

- 1~2자리 숫자 텍스트만
- 한 보표 안에서 **x 가 같은(±3pt) 숫자 두 개가 위아래로**, 세로 간격이 보표 높이의 25~80%
- 분모는 **2의 거듭제곱**(1~32), 분자 1~32
- 같은 박자표가 시스템 **보표의 과반**에서 반복

`ScoreLayout.toMeasures` 는 박자표가 놓인 마디(박자표 x < 마디 오른쪽 경계)부터 다음 박자표 전까지 적용한다. 첫 박자표 이전 마디는 null.
Room **v9**: `score_measures.timeSigNumerator/Denominator`, 기존 분석은 `scoreAnalyzedAt` 을 비워 다시 한다.

분석 시간(에뮬레이터, 13쪽): 190ms → **300ms** (글꼴 해독 추가).

한계: 숫자로 쓰이지 않은 박자표(C, ¢), 경로로 그려진 숫자는 못 읽는다 → 그런 파일은 일반 메트로놈.

## 3. 연동 설계

### `ScoreFollower` (순수)

박 번호 → 악보 위치:

```
박 0 … (시작 마디 박자 − 1)       → 예비박
그다음 각 마디의 박자표 분자만큼   → InMeasure(마디, 마디 안 박, 마디 박 수, 다음 마디)
마지막 마디 이후                   → Finished
```

- **박 = 박자표 아래 숫자의 음표** (6/8 이면 8분음표 6박)
- 박자표가 빈 마디는 앞 마디 박자를 잇는다
- 반복 기호는 따르지 않는다 (악보에 적힌 순서대로)
- 불변 객체라 오디오 스레드가 읽어도 된다

### 메트로놈과 이어 붙이기

- `Beat.index` — 시작부터 몇 번째 박인가 (`MetronomeClock` 이 매긴다)
- `MetronomeEngine.barPosition` — 박 번호 → 마디 안 위치. 주면 **강박을 악보 박자표대로** 둔다(박자가 바뀌어도)
- 화면 쪽은 기존 틱(매 프레임)에서 `currentBeat()`(= **실제 재생 위치**를 지난 박, #047)을 `ScoreFollower` 에 넣는다 — 소리와 표시가 같은 시계

## 4. 화면

### 흐름

1. 메트로놈 대화상자 **시작** → 악보 분석(캐시 있으면 바로) → 박자를 아는 마디가 없으면 일반 메트로놈
2. **시작 마디 고르기**: 현재 화면 첫 마디에 파란 커서. `←→` 마디, `↑↓` 이전/다음 줄 첫 마디, `OK`(뗄 때) 시작, 뒤로 취소.
   커서가 화면 밖 마디로 가면 넘긴다. 이 동안 OK 길게 누르기 메뉴는 뜨지 않는다
3. **예비박** 한 마디 — 시작 마디에 파란 커서 유지
4. **연주** — 현재 마디를 노란 채움으로. 강박은 악보대로
5. **자동 넘김** — 다음 마디가 다른 페이지면 **이 마디가 끝나기 2박 전**(`TURN_LEAD_BEATS`)에 넘긴다. 짧은 마디는 마디 안에서만 당긴다
6. 악보 끝에서 멈춤. 연주 중 **뒤로**는 뷰어를 나가지 않고 메트로놈만 멈춘다

### 넘김이 쌓이지 않게

`ensureMeasureVisible` 은 매 프레임 불린다. 두 페이지 모드는 지금 펼침의 홀짝을 유지하고, 넘김 애니메이션 중이면 다음 틱에 다시 시도하며,
**같은 요청은 1.5초 안에 반복하지 않는다** — 캐시 미스로 렌더가 늦을 때 `showPage` 가 프레임마다 쌓이는 것을 막는다.

### 오버레이

`ScoreOverlayView` 에 **강조 마디 하나**를 더했다: `CURSOR`(파란 테두리, 고르기·예비박), `CURRENT`(노란 채움, 연주 중). 마디 박스 전체 표시
(분석 확인용)와 독립이라 그 옵션이 꺼져 있어도 보인다.

### 에뮬레이터 흐름 (API 30 TV, 임시 계측 테스트 — 커밋 안 함)

키는 같은 프로세스에서 주입하고, 대화상자 "시작"과 같은 메서드를 불렀다. 240 BPM(6/8 한 마디 = 1.5초).

| 시점 | 상태 |
|---|---|
| 시작 직후 | 고르기, 커서 = 1번 마디 (현재 화면 첫 마디) |
| `→ →` | 커서 3번 마디 |
| `↓` | 커서 5번 마디 (다음 줄 첫 마디) |
| `OK` | 예비박, 5번 마디 파란 커서 |
| +3초 … +13초 | 6 → 7 → … → 13 번 마디, 약 1.5초마다 |
| **+14초** | **13번 마디를 연주하는 중에 3·4쪽으로 넘어감** (2박 전) |
| +15초 … | 14, 15, 16 번 마디 |
| 뒤로 | 정지, 뷰어에 남음 (`finishing=false`) |

스크린샷으로 파란 커서(5번), 예비박 박 표시(6점), 노란 현재 마디(7번), 넘긴 뒤 3·4쪽의 15번 마디를 확인했다.

에뮬레이터 캡처는 앱 **내부** 저장소(`filesDir`)에 둬야 `run-as` 로 가져올 수 있었다 — API 30 에서는 셸도 `run-as` 도 `Android/data` 를 못 읽는다.

### 발견한 화면 문제

6/8 처럼 박이 많으면 **왼쪽 위 박 표시가 길어져 악보 제목 앞부분을 가린다**. 연동과 무관한 배치 문제.
→ 사용자 결정으로 위치는 두고 **박 표시 전체를 반투명(불투명도 60%)** 으로 해 가려진 부분이 비치게 했다.
