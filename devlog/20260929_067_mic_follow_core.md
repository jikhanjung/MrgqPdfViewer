## 1. 0단계 — STFT 크로마

- Python `data/score_follow_dtw.py stft_chroma` 를 앱과 같은 계산으로 새로 썼다: Hann 창, 60 ~ 4000Hz 빈을 가장 가까운 반음에 삼각 무게로. 무게는 세기² · 세기 · log 셋을 비교
- 공정한 비교를 위해 **기준 경로를 한 번 만들어 저장**(`--ref-save` / `--ref-load`)하고 모든 실행을 같은 잣대로 쟀다.
  처음에는 칸 크기를 바꾸면 기준 경로(20초 조각 + DP)도 다시 만들어져 곡의 일부만 이어 비교가 어긋났다(286초만 비교)

| 온라인 추적 특징 | ±1마디 | 넘김 ±2초 | 가려짐: 온전 / 반 쪽 |
|---|---|---|---|
| CQT 23ms (P08 기준) | 90% | 89% | 0 / 0 |
| CQT 46ms | 90% | 93% | 1 / 0 |
| **STFT 세기 46ms (채택)** | 88% | 93% | 1 / 0 |
| STFT 세기² 46ms | 86% | 78% | 2 / 0 |
| STFT log | 추적이 멈춤 | | |

- 채택: **44.1kHz · 창 4096 · 걸음 2048(≈ 46ms), 세기 무게**. CQT 보다 조금 못하지만 반 쪽 넘김이면 가려짐 0
- 46ms 칸이 23ms 보다 나쁘지 않다 → 계산량 절반

## 2. 1단계 — `follow/` 패키지

| 파일 | 내용 |
|---|---|
| `ChromaExtractor` · `Fft` | 소리를 조금씩 넣으면 칸마다 크로마. 기수 2 반복형 FFT. 반음 반올림은 numpy 와 같이 짝수 쪽(`kotlin.math.round`) |
| `ScoreChroma` | MusicXML → 같은 칸의 기준 크로마(친 뒤 0.6초로 줄어듦). 마디 시작은 박자표로. 칸 ↔ 4분음표 ↔ 연속 마디 위치 |
| `OnlineAligner` | OLTW(±3초 띠, D/(걸음 수) 최소, 앞으로만) + 재위치(1초마다 30초 창을 ±40초 악보에 부분 DTW, 끝 5초로 판정, 1.15배, 평균 빠르기로 후보) |
| `PageTurnDecider` | 연속 마디 위치 → 반 쪽 넘김(아래 절반 첫 마디 + 1초) · 쪽 넘김(다음 쪽 마디 + 1초) |

- librosa 부분 DTW 를 그대로 옮겼다 — 걸음 순서(대각 · 가로 · 세로, 같으면 앞의 것), 첫 줄은 비용 그대로, 되짚기는 첫 줄에 닿으면 멈춤
- OLTW 누적 배열은 띠 안만 쓰고 지난번에 쓴 곳만 비운다(칸마다 새로 만들지 않음). 재위치 DTW 배열은 가장 큰 크기로 한 번

## 3. Python 과 같은가

- 비교 자료(`data/recordings/fixtures/`, 저장소 밖 — 없으면 테스트 건너뜀)를 Python 에서 내보냈다: 60초 소리와 그 크로마, 녹음 전체 크로마 · 악보 크로마 · Python 경로
- 크로마: 최대 차이 < 1e-3
- 정렬: 처음엔 **87% 만 같았다**(재위치 70번 vs 80번). 원인은 Python 경로는 float64 입력, Kotlin 은 float32 로 내보낸 입력으로 돌린 것 — Python 도 같은 float32 입력으로 다시 돌리니 **19,694칸 모두 같고 재위치 70 = 70**
- 교훈: 대조 시험은 **입력 정밀도까지** 같게. 재위치의 "1.1배 안 후보"같은 문턱은 작은 수치 차이로도 갈린다
- 속도: JVM 에서 915초 녹음 전체가 약 13초(실시간의 70배)
